# Changesets Release Architecture Design

**Status:** Proposed

**Issue:** #47

**Related:** #16

## Goal

Replace Release Please with the maintained Changesets stack as the single release/versioning source of truth for this pnpm/Turbo workspace, while preserving npm Trusted Publishing/OIDC, provenance, existing package verification, GitHub Releases, and least-privilege workflow permissions.

## Context

The repository is a pnpm workspace with multiple packages under `packages/*`. `eslint-config-yarapa` is public and publishable; `typescript-config-yarapa` is private/internal. Release Please currently infers release intent from conventional commit history and maintains its own manifest/config state. That works for a single package, but it is a weaker fit for a workspace where release intent should be declared explicitly per package and per change.

Issue #16 already requires a maintained OSS release tool, npm Trusted Publishing/OIDC, provenance, no long-lived `NPM_TOKEN`, no YARAPA-specific release state machine, and package validation before publish. Changesets is the preferred architecture because it records package impact, semver bump, and release note in the feature PR itself.

## Decision

Adopt:

- `@changesets/cli` v3 at the workspace root.
- `changesets/action` v2, pinned to an immutable full commit SHA.
- Official Changesets v2 sub-actions rather than the all-in-one action:
  - `changesets/action/select-mode`
  - `changesets/action/version`
  - `changesets/action/pack`
  - `changesets/action/publish`
- npm Trusted Publishing / OIDC for registry authentication.
- GitHub Releases and git tags generated by Changesets from the published package versions.

Remove Release Please entirely. Do not keep a hybrid fallback.

## Why split Changesets sub-actions

The Changesets v2 documentation recommends individual sub-actions when using Trusted Publishing because they allow permissions to be isolated by job.

The resulting permission boundary is:

- `select-mode`: no write permissions.
- `version`: `contents: write`, `pull-requests: write`.
- `pack`/verification: read-only repository access.
- `publish`: `contents: write` only if tags/releases require it, plus `id-token: write` for npm Trusted Publishing.

`id-token: write` must never be granted to the version-PR job.

## Release source of truth

Changeset files under `.changeset/*.md` become the only source of semver/release-note intent.

A normal release-impacting PR adds a changeset such as:

```md
---
"eslint-config-yarapa": minor
---

Add canonical Next.js preset support.
```

Commitlint/conventional commit conventions remain useful for commit hygiene only. They do not determine semver.

Private/internal packages must stay non-publishable. The current `@repo/typescript-config-yarapa` package remains `private: true`; Changesets may track dependency/version effects internally only if needed, but the release workflow must never publish it.

## Target developer flow

```text
feature branch
  -> code/docs/tests
  -> pnpm changeset
  -> choose affected publishable package(s)
  -> choose patch/minor/major
  -> write release note
  -> PR + CI
  -> merge to main
```

For changes that intentionally have no release impact, contributors may create an empty changeset using the standard Changesets mechanism rather than a YARAPA-specific exemption database or bot.

## Target automation flow

```text
push to main
  -> checkout + pnpm install
  -> changesets/action/select-mode
       |-- version
       |    -> changesets/action/version
       |    -> create/update "Version Packages" PR
       |
       |-- publish
       |    -> build/test/typecheck/package verification
       |    -> changesets/action/pack
       |    -> validate packed tarball / publint / attw / consumer smoke
       |    -> changesets/action/publish
       |    -> npm Trusted Publishing/OIDC
       |    -> npm provenance
       |    -> git tag + GitHub Release
       |
       `-- none
            -> no release work
```

The exact job graph may split verification and publish into separate jobs if artifact hand-off via the official `pack` sub-action provides a cleaner permission boundary. No custom release-state file or script may be introduced.

## Package verification before publish

The publish path must preserve existing release-confidence checks. At minimum:

- workspace lint
- package typecheck
- package build
- package tests
- real packed-consumer verification
- `publint`
- `@arethetypeswrong/cli`

The package must be rebuilt in CI. The release process must not trust an arbitrary developer-produced artifact.

Where the official `changesets/action/pack` sub-action is used, the exact packed package that is subsequently published should be the one validated whenever practical. Validation must remain consumer-oriented rather than only checking source files.

## npm Trusted Publishing

Publishing must continue to use npm Trusted Publishing:

- no `NPM_TOKEN`
- no long-lived npm automation credential
- `id-token: write` only on the publish job
- npm CLI/runtime versions must satisfy Trusted Publishing requirements
- npm Trusted Publisher configuration must identify this GitHub repository and the final release workflow filename

The workflow must not write a token-based `.npmrc` that disables or bypasses the normal Trusted Publishing OIDC exchange.

Provenance should come from the supported npm Trusted Publishing path, not from a custom signing layer.

## GitHub tags and releases

Changesets must create git tags and GitHub Releases from the same package versions that were published to npm. For the public package, the tag convention must be stable and package-scoped so future additional public packages do not collide.

GitHub Releases must not be created before npm publication has succeeded. A failed npm publish must not leave a release falsely marked as successful.

## Workflow trigger and concurrency

The release workflow runs on pushes to `main`.

Add concurrency so only one release-state transition for `main` runs at once. The workflow must avoid two parallel runs racing to create/update the version PR or publish the same version.

Do not cancel an in-progress publish once it has entered the publishing phase; a newer push should queue rather than interrupt registry publication.

## PR changeset validation

CI should verify release intent for pull requests without inventing a YARAPA-specific policy engine.

Preferred mechanism:

- use Changesets' own status tooling/action where it fits cleanly, or
- run the official Changesets CLI status command against the base branch.

Requirements:

- release-impacting package changes should carry a changeset;
- empty changesets are the standard explicit no-release signal when needed;
- docs/chore-only PRs should not require ad-hoc labels or a custom exemption database;
- the check should fail with a concise contributor-facing message.

## Files removed

The migration removes:

- `.github/workflows/release-please.yml`
- `release-please-config.json`
- `.release-please-manifest.json`

PR #46 (`chore(main): release eslint-config-yarapa 0.3.0`) is a Release Please artifact and must be closed without merge during migration.

No Release Please branch or configuration is retained as fallback architecture.

## Files added or changed

Expected repository changes:

- root `package.json`: add `@changesets/cli` and standard scripts such as `changeset`, `changeset:status`, and/or `version-packages` only where useful.
- lockfile: resolve the approved Changesets versions.
- `.changeset/config.json`: standard Changesets config.
- `.changeset/README.md`: generated/standard contributor guidance if created by Changesets initialization.
- `.github/workflows/release.yml` (or equivalent canonical name): Changesets version/publish automation.
- CI workflow: Changesets status check for PRs if not naturally covered in the release workflow.
- contributor/release documentation: describe adding a changeset and the Version Packages PR flow.
- remove all Release Please config/workflow files.

Avoid helper scripts unless an existing package verification command already provides the required behavior. Prefer maintained CLI/action behavior over shell glue.

## Migration sequence

1. Add Changesets dependencies/config and workflow on a migration branch.
2. Add changeset validation and contributor documentation.
3. Remove Release Please files from the same migration branch so the resulting main branch has exactly one release architecture.
4. Close PR #46 without merge before merging the migration PR.
5. Run all normal CI and review gates on the migration PR.
6. Merge only the migration PR.
7. Verify a push to `main` creates/updates the Changesets Version Packages PR when a changeset is present.
8. Do not publish during migration verification.
9. Configure/verify npm Trusted Publisher against the final workflow filename.
10. Only after Trusted Publishing is verified should a Version Packages PR be merged to exercise the real publish path.

## Safety constraints

During migration:

- do not publish to npm;
- do not create a release tag manually;
- do not merge PR #46;
- do not merge an automatically generated Changesets version PR merely to test publishing;
- do not add PATs, `NPM_TOKEN`, GitHub App secrets, or custom release credentials;
- do not weaken existing CI, security, rulesets, or package verification;
- do not create a second independent publishing workflow.

## Failure behavior

Version-mode failures leave `main` unchanged except for the already-merged feature changes and can be retried safely.

Publish-mode failures must stop before GitHub Release creation if npm publication has not succeeded. Retrying must rely on Changesets/npm's maintained published-version detection rather than a custom recovery state machine.

If a package version is already published, the workflow must defer to Changesets' normal publish detection rather than forcing a republish.

## Acceptance criteria

- `pnpm changeset` works from the workspace root.
- A feature PR can declare `patch`, `minor`, or `major` for `eslint-config-yarapa`.
- A push to `main` with changesets creates or updates the Changesets Version Packages PR.
- Merging the Version Packages PR enters publish mode.
- Publish mode rebuilds and runs the existing package confidence checks before registry publication.
- npm publication uses Trusted Publishing/OIDC with no `NPM_TOKEN`.
- npm provenance is generated by the supported Trusted Publishing path.
- GitHub tag/release and npm package version are aligned.
- `id-token: write` exists only on the publish path.
- `@repo/typescript-config-yarapa` cannot accidentally publish.
- Release Please configuration/workflow is fully removed.
- PR #46 is closed without merge.
- No custom release state machine, approval bot, manifest database, or bespoke release script is introduced.

## Non-goals

- Redesigning commit conventions.
- Replacing pnpm or Turbo.
- Publishing the internal TypeScript config package.
- Adding a YARAPA-specific release dashboard, certification database, or approval service.
- Performing the first real npm publish as part of the migration PR.
